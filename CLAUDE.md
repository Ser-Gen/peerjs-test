# PeerKit

A mobile-first static web app for peer-to-peer tools built on peerjs (WebRTC). Up to 8 devices share a room (QR code, link, 4-word code or recent rooms) and use the tools over it; the room keeps working when anyone leaves. Tools so far: Chat (messages and files with a shared history, files kept for the room, a viewer), Stream (camera and screen, with pointing and drawing on them), Editor (shared documents), Whiteboard (boards drawn together, with pictures from the clipboard) and Controller (a phone as a game pad for another member, and the Monitor that shows what arrives), and everyone in the room can talk over voice chat. Android Chrome and desktop browsers are the targets. The UI is in English.

`PLAN.md` is the roadmap: vertical slices, each with a checklist the user ticks. When a slice is done, update its **As built** section.

## Restriction

**Do not use git.** No commits, branches, diffs, status or any other git command. The user handles version control.

## Commands

The app has no build step. There are two package.json files, neither in the repo root: `vendor/editor-src/` builds `vendor/yjs.js`, `vendor/editor.js` and `vendor/monaco.*` once (the results are committed) and `test/` holds jsdom for the DOM tests. Never run npm in the repo root, and delete `vendor/editor-src/node_modules` after a rebuild.

- Serve locally: `python3 -m http.server`, then open `http://localhost:8000`
- Syntax check: `for f in app/*.js app/*/*.js app/*/*/*.js; do node --check "$f"; done`
- Tests: `node test/run.mjs` (one name to run one, `--times 20` to repeat the random anchor handover). See `test/README.md`; the `dom/` tests need `npm install` in `test/`.
- npm here has `min-release-age=21`: pin versions at least 21 days old instead of overriding it.
- Icons after editing `icon.svg` (ImageMagick renders SVG badly, so QuickLook does the rendering; QuickLook draws onto opaque white, so the rounded icons are rendered square and their corners cut with a mask, never from a render of the rounded SVG. The square copy is also iOS's, which masks the corners itself, and the maskable one is the icon at 72 % on a full-bleed background, inside Android's safe circle):
  `sed 's/ rx="14"//' icon.svg > /tmp/icon-square.svg && qlmanage -t -s 1024 -o /tmp /tmp/icon-square.svg`,
  `magick -size 1024x1024 xc:none -fill white -draw 'roundrectangle 0,0 1023,1023 224,224' /tmp/mask.png && magick /tmp/icon-square.svg.png /tmp/mask.png -compose DstIn -composite /tmp/rounded.png` (224 = rx 14 of 64),
  then `magick /tmp/icon-square.svg.png -resize 180x180 -alpha off -strip apple-touch-icon.png`,
  `magick /tmp/rounded.png -resize 192x192 -strip icon-192.png` (also 512),
  `magick /tmp/rounded.png -resize 48x48 -strip ico48.png` (also 32 and 16) `&& magick ico16.png ico32.png ico48.png -type TrueColorAlpha favicon.ico` (without `-type`, the 16 px entry becomes a palette image and loses its transparency).
  The maskable one: build `/tmp/icon-maskable.svg` as icon.svg with its two rects (the background and the border) replaced by `<rect width="64" height="64" fill="url(#bg)"/>` and the other shapes inside `<g transform="translate(32,32) scale(0.72) translate(-32,-32)">`, render it the same way, then
  `magick /tmp/icon-maskable.svg.png -resize 512x512 -alpha off -strip icon-maskable-512.png`. The pwa test checks the corners and the .ico's entries.
- Phone testing needs HTTPS (the GitHub Pages URL). Camera, sensors, clipboard, Wake Lock and Web Locks don't work on `http://<lan-ip>`.
- Browser testing isn't expected: check logic with the tests in `test/` instead, and add to them when a slice adds behaviour. Stub `window`, `document`, `localStorage`, `navigator`, `location` and a fake `Peer` before importing: `util.js` and the stores touch those globals at import time. `Room` takes an `identity` ({id, name}) so several simulated devices can run in one process.

## Things that aren't obvious

- **Room code:** 4 words from the BIP-39 list (about 44 bits), e.g. `amber-otter-quiet-lamp`. The first 4 letters of each word are unique, so `parseRoomCode` accepts prefixes. The code is the only key: anyone who has it joins without approval, and there is no removal (a new room is the way to exclude someone).
- **Derived from the code** (`roomIds`, SHA-256 with a label each): the room ID (storage key for room data), the anchor peer ID `pk-<hash>` (the server never sees the code) and the HMAC key for the handshake.
- **Link format:** `#room=<code>&s=<base64url profile>&r=<TURN credentials>`. `s` is left out for the public server. `r` carries temporary credentials, never the secret. main.js stores the room as current and removes the hash from the address bar. An old `#join=` link shows "Link from an older version".
- **Anchor:** whoever holds the anchor peer ID lets newcomers in over an `entry` connection: handshake, then `welcome` with the member list; the newcomer dials every member. It gives no rights.
  - A known room (made here or opened before) tries to claim the anchor first; `unavailable-id` means someone holds it, so it connects to it instead. An unknown room only looks, and nobody there is `not-found` ("Wait in this room" claims it).
  - When the anchor's link drops or it says `anchor {held:false}`, members check after 0.5 s and claim after a random 0–3 s; the server lets one win.
  - Every 30 s a member not linked to the anchor holder connects to the anchor again, which merges split groups.
  - A holder that drops off the network keeps the ID until the server notices (about 100 s on 0.peerjs.com). A clean close frees it at once.
- **Links:** one per pair of members, each its own `Link` object (connecting → authed → up → closed, used once), so stale callbacks can't touch a newer link.
  - Handshake: `hello` both ways, then `proof`; the proofs are HMACs over role, nonces, both peer IDs and both DTLS fingerprints, so a relay in the middle fails.
  - Two links to one member: the dial from the lower peer ID wins unless the existing link is alive. The same device ID with a new peer ID (a reload) replaces the old link.
  - After a drop the lower peer ID dials again, up to 6 times. `bye` (Leave), `peer-unavailable` and rejections end it.
  - Tool messages that arrive between authed and up are held and delivered after `link-up`.
  - The **fast channel**: once up, both ends open a negotiated RTCDataChannel (id 16, unordered, `maxRetransmits: 0`) on the ctl connection's RTCPeerConnection, so it needs no signaling. `room.sendFast(ch, msg, to)` sends on it (falling back to ctl where there is none); messages arrive as `msg:<ch>`, and `sys` / `rtc` are never taken from it. Only the Controller's input uses it.
  - Members send `links` (their direct links) so the editor can forward to members that aren't linked to each other. They also fill gaps in the mesh: two newcomers welcomed at the same moment aren't on each other's list, so a member listed by others that this device isn't linked to is dialed once the lists have been still for 3 s (`_meet`), by the lower peer ID of the two. A peer ID that said `bye`, was rejected, or reloaded under a new ID (`gone`) isn't dialed that way.
- **peerjs quirks:**
  - A peer whose first registration fails is destroyed; one that was registered before is only disconnected (`reconnect()` works on it).
  - `connect()` while disconnected returns `undefined`.
  - `peer-unavailable` arrives only as a peer error, with the ID only in the message text ("Could not connect to peer …"), after the server's expire timeout (about 5 s); the connection is never closed.
  - A device holding the anchor has two Peer objects (member and anchor); both share the `config` object.
  - Its websocket to the server can go quiet without closing (peerjs sends heartbeats but never expects an answer), and `socket.send` drops a message without a word when the socket isn't open. Data links don't care once they are up; a call negotiated through the server did, which is why calls go over the links (see **Media calls**).
  - The log level is global, so always pass `debug: 1`.
- **Room states:** idle → starting → joining → open, or failed. `open` stays while the device is in the room, alone or not; members come and go as `link-up` / `link-down` / `members` events. `signalingLost` doesn't change the state: links keep working.
- **Two DataConnections per link:**
  - `ctl` is JSON with messages under ~16 KB, so long text is split.
  - `file` is raw binary: frames of `[u32 transfer id][bytes]`, with backpressure through `bufferedAmount`.
- **One open room per device:** Web Lock `peerkit:room`. A second tab shows "Open in another tab" and can take over with `steal`.
- **Layout:** `app/ui/layout.js` gives each tool one element for its whole life and shows it under the bottom tabs, or as a dockview panel when `(min-width: 900px) and (pointer: fine)` matches; crossing that width moves the elements and never remounts a tool. dockview (`vendor/dockview.js` + `.css`) is loaded only then. Panels use the `always` renderer, so a tool out of sight stays in the page, as with tabs; videos that were playing are started again after a move. `visible()` must ask the panel's group as well: dockview calls panels in a group hidden by a maximize visible. The layout is saved as `peerkit.layout` (version 1) and ignored if it holds a tool this version doesn't have; a tool added since it was saved joins the main area as a tab behind the one in front. The default is Stream, Editor, Whiteboard and Controller in the main area and Chat at the side. Tools can't be closed (no close button). A tool can open panels of its own while docked (`ctx.openPanel`, ids `<tool>:<id>`, one per stream), which have a close button that calls its `onClose`; switching to tabs or Reset layout closes them without it, and the tool puts their elements back from `ctx.onLayout`. They are left out when a saved layout is read.
- **Tools:** a tool is `{ id, title, supported(), mount(el, room, ctx) → unmount }`, where `ctx = { room, activate(), notify(), visible(), onShow(fn), onShare(fn), voiceActive(), onVoiceChange(fn), handOff(toolId, file), onHandOff(fn), docked(), onLayout(fn), openPanel({id, title, el, onClose}) }` and `ctx.room` is the room ID. `handOff` gives a file to another tool and brings it to the front (the viewer's "Open as shared document" → the Editor, a board's PNG → the Chat's send sheet). Tools use `room.members`, `room.member(peerId)`, `room.send(ch, msg, to?)`, `room.sendBinary(to, data)`, `room.call(to, …)` and the events `msg:<ch>` / `binary` / `call` (with the member). Tools mount when the room first opens and stay mounted.
- **Shared editor:**
  - One Y.Doc per room: map `docs`, id → Y.Map `{name, lang, created, text: Y.Text}`, stored in IndexedDB as `peerkit.doc:<room ID>` through y-indexeddb. Leave and forget deletes that database.
  - The data needs only `vendor/yjs.js`, which loads the first time the Editor tab opens, or when the first `doc` message arrives. Messages that arrive earlier are queued with their member.
  - A document shows in **CodeMirror** (`cm-view.js`, `vendor/editor.js`) or **Monaco** (`monaco-view.js`, `vendor/monaco.js`), as chosen in Settings → Editor (`peerkit.editor` `engine`: `auto` is Monaco where `(pointer: fine)` matches, CodeMirror on a touch screen). Each loads with `import()` the first time a document opens in it; changing the choice moves the open document to the other one with its cursor. Both views have the same methods, so `editor.js` doesn't know which it has. Members with different editors share everything, cursors included.
  - Monaco's binding (`monaco-binding.js`) is PeerKit's own, not `y-monaco`: it writes the cursor in y-codemirror.next's awareness field (`cursor: {anchor, head}`, relative positions), undo is the document's `Y.UndoManager` (Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y are rebound to it, since Monaco's own undo would also take back the others' edits), the model's EOL is LF so offsets match the Y.Text's, and a remote name is a content widget's text, never CSS.
  - Another member's name above their cursor can cover a word: pointing at it fades it out (`opacity: 0` on `:hover`, not `display: none`, so the pointer stays on it and it doesn't flicker back; in CodeMirror the rule in `code.js` must beat y-codemirror.next's `.cm-ySelectionCaret:hover > .cm-ySelectionInfo`), and on a touch screen a tap on a name hides all of them for 3 s (`names-peek` on `.editor-host`, editor.js).
  - The provider (`app/docsync.js`, shared with the room document) keeps a `LinkState` per member (queue, split parts); it is also the Yjs origin of what arrives on that link. Messages are base64url on ctl, split into `part`s under the 16 KB limit and paced by `room.controlBuffered(peerId)`.
  - Every link up sends sync step 1 and all known awareness states. Updates from a member are forwarded only to members not linked to it. A link down removes the awareness states heard only through it (and their clocks) and resyncs with the others.
  - Line breaks must be `\n` in the Y.Text: both editors count a line break as one character.
- **Chat:**
  - The timeline lives in the room document (`app/roomdoc.js`, IndexedDB `peerkit.room:<room ID>`, ch `room`), which needs only `vendor/yjs.js` and loads when the room opens: array `chat` of `{id, kind: 'text'|'file', from (device ID), name, time, text | file: {name, size, type, keep, hash}}`, map `held` (`<file id>:<device ID>` → who keeps a copy), map `removed` and map `reads` (device ID → `{id, name, time}`: the newest message that device has had in view, which counts as read together with everything before it; it only moves forward, trimming deletes marks that point at trimmed messages). Everything read from it is validated (`readMessage`). Over 5000 messages the oldest are deleted, the same on every device, and their files are let go.
  - Read marks are written by the Chat while it is on screen (`ctx.visible()` and a visible page), 0.4 s after a scroll, a new message, coming back to the tab or focus: the newest message whose bottom edge is inside the feed. Your own messages show "Read", "Read by <names>" or "Read by all" (everyone online now has read it; the title lists names). Nothing is shown under others' messages, and there is no setting to turn it off yet.
  - A newcomer gets the history by the normal sync. Local "joined" / "left" lines are not in the document; they sit after the message that was last when they happened. The page shows the newest 200 messages, reusing nodes by id; "Show earlier" adds 200.
  - Every file goes through the send sheet with **Keep for the room** (`peerkit.chat`). **Send once**: pushed to the members online, held in memory ("Not kept" for the others). **Kept**: the sender reads it once to store its own copy and hash it (SHA-256 over the SHA-256 of 4 MB parts, so it is computed as bytes arrive), then announces it; receivers write it to OPFS (`peerkit-kept/<room ID>/<file id>`) and check the hash before keeping it. Later, Open/Download asks a member listed in `held` who is online (`want` → `queued` or `none` → `offer` with `req`), one request at a time per member.
  - An offer must match its chat entry, and a device refuses an offer for a file it already has or is already receiving: a bad copy would otherwise overwrite a good one. `transfer` messages call the file's type `mime`, because `type` is the message type.
  - One storage limit for all rooms (Settings → Kept files, `peerkit.files`, default 2 GB): the oldest kept files are dropped first and remembered per room, so the card says so. Kept files need a secure context (OPFS); on `http://<lan-ip>` files are held in memory only.
  - The viewer never runs what a member sent: every object URL gets a type chosen from the file name (downloads are `application/octet-stream`), HTML and code show as source in a read-only CodeMirror, SVG only through `<img>`. PDFs use the browser's viewer where `navigator.pdfViewerEnabled`, else `vendor/pdf.js` (canvas only).
- **Whiteboard:**
  - Boards live in a Y.Doc of their own (`peerkit.board:<room ID>` in IndexedDB, ch `board`, a `RoomDoc` with awareness), not in the room document: images make it large, and a newcomer shouldn't wait for them to see the chat. It loads when the tab is shown or when a member starts syncing it. Map `boards`: id → Y.Map `{name, created, items: Y.Array of Y.Map}`; a stroke is `{kind: 'pen'|'highlighter', from, time, x, y, color, size, points}` with the points packed as little-endian float32 (x, y, pressure) in a Uint8Array, an image `{kind: 'image', from, time, x, y, w, h, data}`. `x`/`y` move a stroke without rewriting its points. Everything read is checked (`readItem`, and `readLiveStroke` for awareness).
  - A stroke in progress goes only through awareness (`stroke`, simplified, at most 15 updates a second); the finished one is simplified (Ramer–Douglas–Peucker: 0.5 screen px, and pressure within 0.05 so a stylus keeps its taper) and stored in one transaction. Undo is a `Y.UndoManager` per board with `trackedOrigins` = the local origin and `captureTimeout: 0`: each stroke, erase gesture, move or image is one step, and only this device's own.
  - Input: Pointer Events on a `touch-action: none` stage, every pointer captured. A lost capture ends a gesture as a release, so the stroke is kept (Chrome sometimes takes the capture away just before the mouse button comes up); a `pointercancel` drops it. Two fingers pinch and pan (a stroke younger than 250 ms when the second finger lands was the pinch's first finger and is dropped); once a stylus has drawn, a finger pans; the wheel pans and Ctrl+wheel (a touchpad pinch) zooms; Space or the middle button drags the view. Two canvases: the board (redrawn on a change or a camera move, only what is in view) and a live layer on top (strokes in progress, pointers, the selection).
  - Images: Ctrl+V on the board or with nothing focused (a paste into a text field stays there), the Paste button (`navigator.clipboard.read`, which asks for permission on Android), a file, or a drop (which stops there, so the Chat's send sheet doesn't open). They are drawn again through a canvas (this drops a photo's location and applies its rotation), at most 2560 px, PNG when that is 1 MB or less, else WebP (JPEG where WebP can't be written), smaller until it fits; at most 40 per board. A member's image is decoded with `createImageBitmap` from bytes without a type, so an SVG never renders.
  - The board is white paper in both colour schemes. Export: the whole drawing as a PNG, 2 px per board unit (4096 px at most), downloaded or handed to the Chat.
- **Media calls** (`app/mediacall.js`, protocol 7): `room.call(to, stream, metadata, {sdpTransform})` makes a `MediaCall` with its own `RTCPeerConnection` (the links' ICE servers, `room.rtcConfig`) and negotiates it over the link on ch `rtc` (`offer {call, sdp, meta}` / `answer` / `ice` / `close`), never through the signaling server: a call works whenever the link does, and needs no server at all. A call exists only while its link is up (`room.call` returns null otherwise, and a link that goes down closes its calls on both sides); incoming offers wait in the link's `early` queue like any tool message. It keeps peerjs's shape (`connectionId`, `peer`, `metadata`, `peerConnection`, `open`, `answer(stream, options)`, `close()`, 'stream' once per track, 'close', 'error'), so voice and the Stream tool didn't change. Unlike peerjs, closing one end tells the other (`close`), and ICE that fails is restarted by the caller over the link twice (`createOffer({iceRestart})`, a new offer with the same call ID) before the call ends. The callee applies the offer before adding its own tracks, so they go out on the offered transceivers. Everything in a signal is checked (`readSignal`: call ID 16 hex, SDP ≤ 32000 characters, metadata a small plain object). Calls that arrive through the server are closed.
- **Voice:** `app/voice.js` is room-level, not a tool: it is mounted from `main.js`, its controls are a row in the room bar (so mute is one tap from every tab) and its `<audio>` elements sit in a container on `body`, outside the tool panels. One call per pair, not per direction: of two members in voice the one with a microphone dials, the lower peer ID when both have one, and the other answers with its own microphone (`metadata.kind === 'voice'`). A device with no microphone, or one that refused it, joins as a **listener**: always muted, never dials, called by the others. Mute is `track.enabled = false` plus a `voice` message, which leaves the call alone; joining and leaving voice do re-make the calls. Who is speaking is measured locally with a Web Audio `AnalyserNode` per stream (never sent), and the others always play through `<audio>` elements so the browser's echo cancellation sees them. Chrome gives a remote stream to a media element **or** to Web Audio, not both, so the analyser gets a clone of the track (`tap()`) and the element keeps the stream it plays — handing it the same stream is silence with working speaking marks. A member in voice who cannot be heard yet is marked `waiting`, not `on` (the room bar says "connecting…", the voice sheet says why), because counting someone in before they can be heard hides every failure below; "can be heard" means their track is here **and** unmuted — a remote track is `muted` until media comes through it, which is also what ends the wait on a call. A call that connects but never delivers audio is closed and dialled again after 10 s, a pair left without a call calls when the room reports `state` again, and the redial slows to one every 15 s instead of giving up. A side that ends a call while both stay in voice (no audio from it, or a listener taking the microphone) also sends `hangup {call}` with the call's `connectionId` (from the peerjs days, when closing didn't tell the other end); the other side ends its end, and the one that dials calls again. A member can be turned up to 200 % (`MAX_VOLUME`): an `<audio>` element stops at 1.0, so above 100 % the element is muted (but stays attached, because Chrome starts a remote stream only through an element) and the sound plays from the tap's copy of the track through a `GainNode` and a limiter (`boost()`), never both, since two copies a few milliseconds apart sound hollow; without Web Audio the slider stops at 100 %. The room bar and the voice sheet are updated in place, never rebuilt: they redraw on every ping answer and every change of who is speaking, and a button replaced between press and release loses its click.
- **Media:** streams go to the whole room (`app/tools/stream.js`, ch `stream`). A member can share a camera and a screen at once. Each is announced to every member (`start {id, kind}`) and sent over a media call per viewer; a member whose link comes up gets every stream running, so a capture started in an empty room waits for whoever arrives. A viewer that closes a stream closes its call, which tells the sender, and keeps a chip to watch it again (`watch {id}`, also Try again after a call gave up). A dropped link pauses the stream on the viewer for 30 s (`GRACE`) and the sender calls again with the same id once the link is back; the sender keeps no pause of its own, and a viewer that closed it closes the new call again.
  - The viewer shows "Connecting…" until the first frame: a call hands over its video track as soon as it is negotiated, `muted` until a frame comes through (`follow()`; a later mute, a still screen, keeps the picture).
  - Where it shows: tiles in the Stream tool's grid (tap to show one large) on a phone or a narrow window, a panel per stream (`ctx.openPanel`) on a wide one; the same tile element moves between them, and a moved video is played again.
  - Camera switch is `replaceTrack` on every call and resolution `applyConstraints` on the one track they share. A phone's camera goes to 480p while more than 2 watch (each call is an encoder of its own).
  - Every 2 s the sender reads `getStats()` per call for the rate and `qualityLimitationReason`; a call held back by bandwidth gets a `maxBitrate` of 85 % of what it gets through (at least 150 kbit/s) and the bar warns, and after 10 s of calm the cap goes up by a quarter until it is taken off. The bar's numbers are updated in place, never by rebuilding it.
  - **Marks** (`stream-marks.js`): Point and Draw on a stream's tile. Positions are fractions of the video picture (after `object-fit` and letterboxing, and flipped on a mirrored preview), never of the element. A viewer sends `mark {id, pt?, st?, clear?}` to the sender only, batched to at most 30 a second (a still pointer is sent again every 2 s and goes away after 6 s unheard); the sender draws it on its preview and passes it on to its other viewers with `by`, so a member that closed the stream gets none and viewers need no link to each other. A viewer takes marks for a stream only from its sender. Strokes stay 3 s after they end, then fade over 1 s; Clear (a viewer's or the sender's) removes every stroke for everyone. A page can't draw on the real screen, so the sender is told once that marks show on its preview only. `mark` came without a new protocol number: older version-8 devices ignore it.
  - Screen audio skips voice processing and is sent as stereo music-bitrate Opus through `sdpTransform`, applied on both the call and the answer.
- **Controller** (`app/tools/controller/`, ch `input`): a member's Monitor (or, later, a game) holds `InputHub.of(room)` and says `host {on}`; controllers list those members and send `state {slot, seq, t, buttons, down, axes, quat?, rtt?}` in the Standard Gamepad order (NES B = 0, A = 1, Select 8, Start 9, D-pad 12–15, the Motion trigger 7). Slot 0 is the screen, 1–4 gamepads plugged into the controller. `InputSender` sends on every change, at most 60 a second per slot and again every 0.5 s, over the fast channel, and a message that changes a button over ctl as well; `down` (buttons pressed since the slot's previous message) lets the hub count a press once whichever copy comes first, and a press whose copy comes after its release as a tap. The hub gives each device's pad a slot of its own (by device ID, so a reload keeps it), emits `pads` / `state` / `press` / `release` and has `getPad(slot)`, shaped like a Gamepad. It echoes the controller's `t` once a second for the latency. Motion is `AbsoluteOrientationSensor` in the screen's frame, else `deviceorientation` turned by the screen angle, relative to the last Recenter. The pad is full screen, landscape and keeps the screen on; it stops when its host leaves or stops hosting.
- **TURN:** a device setting (`peerkit.turn`), not part of a server profile. `IceConfig` owns the `config` object passed to `new Peer()`; peerjs reads it for every new RTCPeerConnection, so credentials are replaced in place. A member with a secret mints 7-day credentials (`forRoom`) for links, `welcome` and a `turn` message on every link up; others adopt credentials only if they expire later, and pass them on. The secret stays on the device.
- **Versions:** `APP_VERSION` in `app/version.js` is `0.<last finished slice>.<fix>` and shows in Settings → About; bump it when a slice is finished, the patch number for work between slices. `VERSION` in `sw.js` names the cache and must be the same string (the pwa test checks it). `PROTOCOL_VERSION` in `app/protocol.js` changes only when messages change incompatibly (8 = streams to the whole room, and later marks on them; 7 = media calls over the links; 6 = the chat in the room document; 5 = rooms with voice; 4 answered every media call as a stream), and members with different numbers refuse to link. A new channel that older devices can ignore needs no new number: the whiteboard's `board` and the controllers' `input` came without one.
- **PWA and the share target:** `sw.js` is a classic worker (Firefox has no module workers) and serves network first with the cache as fallback, so an update is never held back; its `SHELL` must list every file under `app/` and `vendor/` except `vendor/editor.js`, `vendor/monaco*`, `vendor/dockview.*` and `vendor/pdf*.js`, which are cached on first use (a document opened in CodeMirror or Monaco, a text file in the viewer, a wide window, a PDF on Android). `vendor/yjs.js` is in it: the chat needs it at once. An Android share is a POST that a static host can't answer: the worker stores the files and text in the `peerkit-share` cache and redirects to `./?share=1`; `app/share.js` reads that cache once, and only when a room is open, so the share survives the reload that opening a room does. `ctx.onShare(fn)` hands it to the Chat, which opens its send sheet. Cache storage is missing on `http://<lan-ip>`, so every call is guarded.
- **Names:** a rename in Settings (`device` 'change') makes the room send `name` and emit `members`; everything that shows a name listens to `members`, and nothing may keep a copy of one without refreshing it there. The Chat shows a device by its name now (`nameOf`: a member online, else the name its read mark carries, else the one stored with the message), so earlier messages, read labels, "has it" and "Removed by" follow a rename; a device rewrites its read mark with the new name (`timeline.rename()`) so devices that are never online together learn it. The Editor and the Whiteboard put the new name in their awareness `user` (`renameSelf()`), voice copies it into its peers (`onMembers`), and the Stream tool into its tiles and panel titles (`fromName`); a pointer's name on a stream is looked up at every paint. The Controller's hub copies names into its pads on `members` and the Monitor's cards follow; the host chips and the pad's host name are redrawn from `members` too. The Editor uses `room.self.name`, not `device.name`.
- **Stored data:** localStorage data is versioned (`peerkit.settings`, `.room`, `.device`, `.turn`, `.editor`, `.voice`, `.layout`, `.chat`, `.files`, `.whiteboard`, `.controller`); editor documents (`peerkit.doc:<room ID>`), the room document (`peerkit.room:<room ID>`) and the boards (`peerkit.board:<room ID>`) live in IndexedDB, kept files in OPFS. "Leave and forget" deletes all four for the room. `peerkit.rooms` / `.recent` from pairing are only checked for a one-time notice. Validate everything read from storage, links or members, because all of it is untrusted.
- **Settings screen:** it is a history entry (`pushState`), so the Android back gesture closes it. Editors are modal `<dialog>`s. A room stays on the server from its link; the active profile is for new rooms and typed codes.
- **Layout:** `.app` is a flex column, not a grid, so hidden bars don't break the layout. Inputs use 16px text so mobile browsers don't zoom on focus.
- **Code style:** tabs, ES modules and the `h()` element builder. Never use `innerHTML` with untrusted text (see `linkify`). Write control characters in regexes as escapes (`\x00`), never raw.
